# CareerPilot AI implementation status

## JSearch primary with Himalayas fallback — 2026-10-25

- **Search flow**: The authenticated `GET /api/internships/search` route queries JSearch first for Indian roles, then combines eligible Himalayas results. Himalayas remains enabled and is used when JSearch is unconfigured, rate-limited, or temporarily unavailable. Successful results from either source are retained; the response identifies fallback mode and each listing retains its source and original application URL.
- **JSearch filters**: Requests send the requested role/title and location, `country=in`, `employment_types` when selected, and the documented `date_posted` values (`today`, `3days`, `week`, `month`, `all`). Internship searches add an internship term; other employment selections search the requested role without forcing an internship keyword. The location input accepts Indian cities including Chennai, Coimbatore, Vellore, and other locations.
- **Location grouping**: Results are ranked and displayed separately as exact non-remote location matches, remote roles available to India, and broader Indian locations. Non-India listings are rejected; worldwide remote roles are not represented as local matches. Empty results show an explicit no-suitable-jobs message.
- **Duplicate/link handling**: Provider copies are deduplicated across matching company, title, and location. Direct application links are preferred when a duplicate exists; the chosen listing keeps the original provider URL and source name.
- **Caching and quota protection**: Successful JSearch responses are cached in process for five minutes (up to 200 search keys). Rate-limit responses apply a cooldown; exhausted monthly quota suppresses further JSearch calls until the provider reset time when supplied, or otherwise until the next UTC month. Himalayas serves searches during cooldown, and JSearch can resume after the cooldown. Credentials are loaded server-side from `server/.env`; no API key is returned to the client or included in logs/specification.

## Internship listing and Apply Now correction — 2026-10-24

- The Internship Explorer waits for the signed-in user's profile, then searches up to three preferred roles. If no roles are saved, it infers role categories from the resume summary, headline, and skills. The profile's preferred location is used when available; otherwise the search defaults to India.
- Users can search a different role such as Data Analyst. Clearing the role search switches back to the profile-based recommendations. The Explorer loads JSearch results explicitly and provides a bounded **Load more internships** action using JSearch continuation cursors instead of automatic endless loading.
- If one preferred-role request fails, successfully loaded roles remain visible. If every live request fails, the page shows a neutral retry message and does not present the failure as zero listings. Provider rate limits are not retried automatically.
- JSearch results must have an internship title/type, an India location (or remote eligibility that includes India), a valid posting date, and a specific HTTPS job/application page. Results older than 45 days or expired per the provider are excluded.
- JSearch `job_apply_is_direct` and `apply_options[].is_direct` are used when mapping links. A direct option is preferred only when the URL identifies a specific role. Specific platform pages are labeled **View on job platform**; only provider-confirmed direct links are labeled **Apply Now**. Generic search/category pages are rejected, including LinkedIn searches and generic Internshala internship categories. Listings without an exact listing URL are excluded.
- Remotive discovery now includes only recent internship posts whose remote location permits India, with a specific Remotive job page. It no longer fills results with fabricated catalog examples. Its links are labeled **View on job platform**, and the source remains attributed as Remotive.
- The listing and matching APIs hide sample, stale, out-of-scope, invalid-link, and duplicate opportunities. Existing database rows are retained; no records were deleted. Old invalid opportunity detail pages no longer expose the generic link as an Apply action.

## Security and data handling

- Database configuration reads `server/.env` as authoritative, uses the database path in `MONGODB_URI`, and does not apply a fallback database name or separate database override.
- Profile, match, application, resume-version, and notification reads and mutations are scoped to the authenticated user.
- Resume replacement archives prior resume metadata and does not delete existing applications, matches, or versions.
- External application links are opened separately. Application status changes only after the user confirms submission.
- The live Mongo verification script creates a uniquely named temporary account and removes only that account and its profile. No pre-existing records were deleted.
- Secrets, connection strings, and resume contents are not written to this document or verification output.

## Integration configuration

- `HIMALAYAS_API_KEY`: Optional Himalayas credential read by the backend from `server/.env`; credentials are sent only in server-side request headers.
- `JSEARCH_API_KEY`: JSearch RapidAPI credential read by the backend from `server/.env`; it is never returned to the client or written to logs.
- `GEMINI_API_KEY`: Gemini credential read by the backend; requests use the Google-compatible REST API and do not expose the key to the frontend.
- `GEMINI_MODEL`: optional backend model override; defaults to `gemini-3.6-flash`. A live request using the configured model succeeded.
- `MONGODB_URI`: existing MongoDB connection configuration; no database reset or migration was performed.
- `.gitignore` excludes `.env` files while retaining `.env.example`. Credentials were confirmed rotated before live checks in this run. Never put credential values in source, specs, logs, or frontend configuration.
